The problem

Four coordinate systems, two of them upside down to each other

The game logs x, y, z in world units with z pointing north. Images count rows from the top. The trick is to go through a neutral 0 to 1 space in between, and to do it in exactly one place.

# 1 → 2 · projection.py
u = (x − origin_x) / scale
v = (z − origin_z) / scale
# 2 → 3 · space.ts
X = u × 1000
Y = (1 − v) × 1000 × H / W
# 2 → pixel (for checks and figures)
px = u × W
py = (1 − v) × H

The 1 − v is the flip: world z grows north (up the page) while image rows and the drawing space grow down. The H / W factor keeps a non-square image in proportion.

Calibration

Each map is a world square laid over its image

The data README gives a scale and an origin per map: the world square from the origin to origin + scale on both axes covers the whole image. Its formula is right. Its image size is not: it says 1024 px, and none of the three minimaps is.

Why go through 0 to 1 instead of straight to pixels

Images get resized. Lockdown's ${Lockdown_src} px original ships as ${Lockdown_web}, and the README assumed 1024. A position stored as a share of the map is right at every size, so the pipeline stores u and v, and each consumer multiplies by its own width and height. The README's own example lands at the same spot on all three sizes:

Same u = ${ru}, v = ${rv} every time; only the multiplier changes. The README expects (78, 890) on 1024 px.

GrandRift isn't square

Its image is ${gr_w} × ${gr_h}. Treating it as square would put the south edge ${gr_square_err} px off, so width and height are always used separately (drawing space height ${gr_space_h}).

The pipeline side: pipeline/src/lila_pipeline/projection.py

def world_to_uv(map_id, x, z): cal = MAPS[map_id] # scale, origin_x, origin_z u = (x - cal.origin_x) / cal.scale v = (z - cal.origin_z) / cal.scale return u, v # never clamped: callers count # anything outside 0 to 1 def uv_to_pixel(u, v, width, height): px = u * width py = (1.0 - v) * height # rows count down, z counts up return px, py

Shortened from the file. An unknown map name raises an error instead of guessing.

The browser side: web/src/map/space.ts

const SPACE_WIDTH = 1000 spaceHeight(map) = 1000 * map.height / map.width uvToSpace(u, v) = [u * 1000, (1 - v) * spaceHeight] imageBounds(map) = [0, spaceHeight, 1000, 0] # the minimap's BitmapLayer uvToWorld(u, v) = { x: u * scale + origin_x, z: v * scale + origin_z } # cursor readout only

Summarised from the file. Paths, markers, heatmap pictures and hotspot outlines go through uvToSpace, and the image through imageBounds, so they share one space.

Testing it against the art

Getting it wrong on purpose shows the real mapping fits

Every recorded path on Lockdown, drawn three ways on the shipped minimap. There are no surveyed landmarks to check against, so the test is whether the routes fit the roads, buildings and coastline, and whether plausible mistakes visibly don't.

Human paths blue in the production mapping and red in the controls; bot paths amber in all three. Judged by eye, not by a pixel-colour score: dark roads and art make pixel counts unreliable, so the maths on page 7 is the pass/fail part.

Verification

The maths is the pass/fail check; the pictures are supporting evidence

Unit tests pin down the formula's behaviour; a round trip on every exported point shows the two directions agree on real data.

Unit tests: ${tests_py} pipeline, ${tests_web} browser, all passing on ${tests_date}

  • The README's worked example gives (78, 890) on a 1024 px image.
  • World corners land on the image corners and the world centre on the image centre, for all three maps.
  • +x moves right, +z moves up.
  • GrandRift's ${gr_w} × ${gr_h} image scales each axis separately.
  • Values outside the map are reported, never clamped; an unknown map is rejected.
  • The real minimap sizes are checked, and every recorded position falls inside its map's square.
  • Browser: drawing space, cursor back to world, and the inverse of each function.
